# World of Cake Redundancy Reduction Plan

Date: 2026-09-15

This document records the current plan for reducing duplication in World of Cake without flattening the important differences between apps and host targets. The priority is robustness first: Rack timing, persistence, runner hygiene, and build reliability. Broader framework cleanup should follow only after those boundaries are stable.

## Current Direction

World of Cake is moving toward this architecture:

- Haxe owns portable sequencer, automaton, state, and UI reference behavior.
- OpenFL remains the reference UI and interaction implementation.
- Rack uses native C++ shells and runners so the audio thread never calls into Haxe.
- VST/JUCE is a near-term target, so shared host concepts should not become Rack-only unless they are genuinely Rack-specific.
- Layla plus EDN should become the source of truth for panel layout and control details, with target-specific variants where the host requires them.

The intended source layout is:

```text
Source/
    portable Haxe framework and app code

bridge/haxe/
    Haxe harnesses used by native hosts

bridge/native/
    host-neutral C++ bridge/support library

derivatives/vcvrack/
    Rack-specific plugin shells, widgets, Makefiles, and Rack helpers

derivatives/juce/
    future JUCE/VST-specific host implementation

The layout pipeline adds two maintained source areas:

```text
laylagen/
    WoC-owned offline Layla/EDN generators and generator tests

layouts/openfl/
    canonical OpenFL Layla/EDN inputs

layouts/rack/
    Rack-specific Layla/EDN inputs, including Rack-only output sockets
```

Generated results are disposable and must not be confused with source:
`Source/generated/`, `bridge/native/worldofcake/generated/`, and
`derivatives/vcvrack/*/generated/` are regenerated by the build pipeline. Rack
object files, native Haxe output, packages, and local installations belong
under `build/` or other ignored artifact locations.
```

The former top-level `Cpp/` directory has been retired. Its host-neutral coordinate support now lives in `bridge/native/WorldOfCakeBridgeTypes.h`, alongside the rest of the native bridge vocabulary.

The recent Rack work established the important runtime boundary:

```text
Rack module / widgets
    -> ControlCommand queues
    -> native ControlRunner
    -> Haxe Harness
    -> app sequencer/model
    -> POD control and visual snapshots
    -> Rack audio/UI consumption
```

This boundary is sound. The refactor should make it more regular and less duplicated, not replace it with a larger abstraction too early.

## Build And Makefile Situation

There are not separate Makefiles for Linux and Windows. Each Rack module has one small Makefile that declares module identity and includes the shared Rack build rules in `derivatives/vcvrack/common/plugin.mk`. The common include branches internally for Linux and Windows.

The current model is:

- Same per-module Makefile for both platforms.
- Shared build logic in `derivatives/vcvrack/common/plugin.mk`.
- Windows default Rack SDK path: `../../Rack-SDK-2.6.4-win-x64/Rack-SDK`.
- Linux default Rack SDK path: `../../Rack-SDK-2.6.6-lin-x64/Rack-SDK`.
- Windows hxcpp object directory under repo build output: `build/vcvrack/<module>/native/obj/mingw64`.
- Linux hxcpp object directory under repo build output: `build/vcvrack/<module>/native/obj/linux64`.
- Windows adds `-D HXCPP_MINGW` when invoking Haxe.
- Linux does not add an extra Haxe platform define there.
- Windows adds extra linker flags for static libgcc/winpthread handling.

Rack generated artifacts now belong under repo-level `build/`, not under `derivatives/`:

```text
build/vcvrack/<module>/native/       hxcpp generated C++/headers/objects
build/vcvrack/<module>/rack-build/   Rack C++ object/dependency files
build/vcvrack/<module>/plugin.so     Linux local plugin binary
build/vcvrack/<module>/plugin.dll    Windows local plugin binary
build/vcvrack/<module>/dist/         packaged .vcvplugin output
```

`derivatives/vcvrack/<module>/` should contain maintained target source: `src/`, `haxe/`, `res/`, `Makefile`, `plugin.json`, and docs. The old per-module `build/`, `native/`, `dist/`, `plugin.so`, and `plugin.dll` outputs have been removed from `derivatives/` and are gitignored.

Path handling is still asymmetric where useful:

```make
ifeq ($(OS),Windows_NT)
BRIDGE_NATIVE := ../../../bridge/native
else
BRIDGE_NATIVE := $(abspath ../../../bridge/native)
endif
```

The intent is practical, not architectural. Linux uses an absolute `BRIDGE_NATIVE` path to keep Rack SDK build/dependency output from leaking into `derivatives/bridge`. Windows keeps the path relative because MSYS/Windows path handling is more fragile, especially around path conversion and linker arguments.

Makefiles were refactored using Make's `include` mechanism. The goal was not to hide each plugin's identity. The goal was to move repeated host/build machinery into a common include while leaving module-specific declarations in each module.

Example direction:

```make
# derivatives/vcvrack/tileland/Makefile
WOC_MODULE := tileland
WOC_TITLE := TileLand
WOC_RUNNER_CPP := TileLandControlRunner.cpp
WOC_PANEL_SVG := res/TileLand.svg

include ../common/plugin.mk
```

The included file can own:

- Linux/Windows SDK defaults.
- `HXCPP_OBJDIR`.
- Haxe platform flags.
- hxcpp include discovery.
- Rack build platform marker cleanup.
- shared bridge include paths.
- shared `ControlThread.cpp`.
- hxcpp object linking.
- common `clean`, `codegen`, and default build behavior.
- optional panel-title injection rule, parameterized by module name and SVG.

Each module should continue to own:

- module slug/version.
- app-specific C++ source files.
- app-specific runner source selection.
- panel SVG/resource names.
- any exceptional linker or build requirements.

## Robustness-First Priorities

### 1. Centralize Rack Timing Policy

The recent Linux issue exposed a hidden timing policy. Linux was able to wake the control thread close to 1 ms, while Windows likely ran effectively slower due to scheduler/timer behavior. TileLand in particular became too fast and could overload the UI/control path.

Current fixed behavior separates:

- control wake/render cadence: about 60 Hz.
- WoC logical delta: 1 ms.

Those values are currently repeated in module sources. They should be named once.

Recommended common header:

```text
derivatives/vcvrack/common/WocRackTiming.hpp
```

Suggested contents:

```cpp
namespace worldofcake::rack {
constexpr double kControlPeriodSeconds = 1.0 / 60.0;
constexpr double kLogicalDeltaSeconds = 0.001;
}
```

Use these constants from every Rack module when starting its runner:

```cpp
runner->start(
    worldofcake::rack::kControlPeriodSeconds,
    worldofcake::rack::kLogicalDeltaSeconds);
```

Do not expose these values as UI parameters yet. First make the policy explicit and consistent.

Later questions:

- Should Rack modules support a selectable control refresh rate?
- Should logical simulation delta be app-specific?
- Should VST/JUCE share the same logical delta policy?

For now, hardcoded named constants are enough.

### 1a. Move Host-Neutral C++ Coordinates Into The Native Bridge

Status: complete. The host-neutral native coordinate vocabulary was folded into the native bridge layer and the top-level `Cpp/` directory was removed.

Historical context: the top-level `Cpp/` directory contained:

- `Cpp/WorldOfCakeCoordinates.hpp`
- `Cpp/WorldOfCakeCoordinates_test.cpp`

These were introduced while debugging Zewp, but the concepts are not Zewp-specific and not Rack-specific. They mirror the Haxe coordinate vocabulary:

- `ScreenPoint`
- `PanelPoint`
- `LocalPoint`
- `CoordinateMapper`

`bridge/native/WorldOfCakeBridgeTypes.h` already contains many snapshot structs with raw `x` and `y` fields, but it does not define equivalent typed point or coordinate mapper classes. So there is no direct duplicate definition today, but there is conceptual overlap.

Preferred destination:

```text
bridge/native/WorldOfCakeBridgeTypes.h
```

Rationale:

- Coordinate point types are part of the common native vocabulary used at the host bridge.
- Other bridge POD types already live in `WorldOfCakeBridgeTypes.h`.
- Future Rack and JUCE/VST shells should be able to use the same native coordinate terms.
- The top-level `Cpp/` directory is too vague once `bridge/native/` exists.

The test should move to:

```text
bridge/native/tests/WorldOfCakeCoordinates_test.cpp
```

or be renamed if the coordinate types are folded directly into `WorldOfCakeBridgeTypes.h`.

Completed:

1. Folded `BasePoint`, `ScreenPoint`, `PanelPoint`, `LocalPoint`, and `CoordinateMapper` into `bridge/native/WorldOfCakeBridgeTypes.h`.
2. Removed the Zewp-only Makefile include path for `../../../Cpp`.
3. Ensured Rack modules include `bridge/native`, not `Cpp`.
4. Moved the coordinate test under `bridge/native/tests/`.
5. Deleted the top-level `Cpp/` directory.
6. Built Zewp first, then all Rack modules.

This move did not change behavior. It was a layout and ownership correction that makes the native coordinate vocabulary reusable across apps and hosts.

### 2. Delete Obsolete Direct-Haxe Rack Facades

Legacy direct-Haxe Rack facade files duplicate responsibilities now handled by Haxe harnesses and native runners. They come from the older pattern where Rack called into Haxe under a mutex.

The current Rack hxml targets should compile `worldofcake.bridge.*Harness`, not legacy direct-Haxe facades.

Plan:

1. Search for all legacy direct-Haxe facade references.
2. Verify no active hxml, C++, build script, or current document requires them.
3. Delete obsolete facade files.
4. Update docs that still describe the old direct Haxe/mutex model.
5. Build all Rack modules.

Because this repo is still in development, deletion is preferred over archiving. If something breaks, it should break visibly.

### 3. Normalize Persistence

Do not generalize app state serialization.

The project has already found that relying on Haxe native JSON serialization of arbitrary data structures can crash Rack. App state serializers must remain explicit, manual, and app-owned.

The split should be:

Common persistence:

- Rack JSON envelope.
- native mailbox for pending import/latest export.
- thread-safe transfer of opaque state strings.
- generation counters or dirty flags.
- import/export request lifecycle.
- post-import snapshot refresh hook.

App-specific persistence:

- actual JSON state schema.
- manual field serialization.
- manual parsing.
- schema versioning.
- validation and fallback behavior.
- model mutation after import.

The common Rack-facing envelope can be generic because it only wraps an opaque string:

```json
{
  "stateJson": "..."
}
```

The native persistence layer can move strings safely without understanding their contents:

```cpp
submitImport(jsonString);
applyPendingImport();
requestExport();
takeLatestExport();
```

But the app runner still owns:

```cpp
harness->exportStateJson();
harness->importStateJson(jsonString);
```

The important common rule is that after import, the runner must publish fresh control and visual snapshots so Rack parameters and UI redraw state match the restored model.

Initial persistence work:

1. Confirm current `StatePersistence` behavior.
2. Bring Gbloink into line if it still uses a separate inline mailbox pattern.
3. Extract Rack `dataToJson` / `dataFromJson` helpers for the `stateJson` envelope.
4. Add a consistent post-import refresh hook.
5. Build and smoke-test every module.

### 4. Centralize Transport UID Maps

Status: superseded by generated EDN controls.

The early plan was to preserve handwritten transport/control UID values while moving their names into one Rack-facing C++ header. That was useful as an intermediate cleanup, but the later Phase 9F implementation superseded that again by moving common host controls into spatial Layla/EDN components instead:

- reset/pause controls are generated as `:button` / `:toggle` components for all current apps.
- KDiagram rotate controls are generated from spatial `rotate-left` / `rotate-right` button components.
- Gbloink edge-note toggle is generated from a spatial `edge-notes` toggle component.
- Rack modules still have Rack-local `ParamId`s, but their mapping target is now a generated WoC control ID.

## Runner Consolidation

After the smaller Rack common helpers are in place, extract a `ControlRunnerBase` or equivalent.

The repeated runner responsibilities are:

- lifecycle: `start`, `stop`, create model, destroy model.
- control thread ownership.
- command queue ownership.
- command drop/high-water accounting.
- pending command application.
- state persistence handoff.
- control snapshot generation counter.
- visual snapshot generation counter.
- import/export lifecycle.

The app-specific runner responsibilities should remain app-owned:

- harness type.
- harness creation.
- app command dispatch.
- reset/pause/rotate semantics.
- snapshot field extraction.
- event draining, where applicable.
- output topology.

Possible C++ shape:

```cpp
template <typename Harness, typename ControlSnapshot, typename VisualSnapshot>
class ControlRunnerBase {
public:
    bool start(double periodSeconds, double logicalDeltaSeconds);
    void stop();
    bool enqueueCommand(const ControlCommand& command);
    bool latestControlSnapshot(ControlSnapshot& out) const;
    bool latestVisualSnapshot(VisualSnapshot& out) const;

protected:
    virtual Harness* createHarness() = 0;
    virtual void destroyHarness(Harness*) = 0;
    virtual void applyAppCommand(Harness&, const ControlCommand&) = 0;
    virtual void captureControlSnapshot(Harness&, ControlSnapshot&) = 0;
    virtual void captureVisualSnapshot(Harness&, VisualSnapshot&) = 0;
    virtual void afterImport(Harness&) {}
};
```

This is only a sketch. The exact C++ design should be driven by the existing runner code and kept easy to debug.

Refactor sequence:

1. Normalize persistence first.
2. Pick one simple runner as the pilot.
3. Extract common lifecycle and queue mechanics.
4. Keep app dispatch and snapshots outside the base.
5. Build and test the pilot.
6. Migrate the rest one at a time.

Do not combine this with Makefile refactoring in the same commit.

## Haxe Sequencer Lifecycle

The Haxe apps repeat similar transport and event queue logic:

- `currentTime`.
- `events`.
- `paused`.
- `dirty`.
- `pause`.
- `resume`.
- `reset`.
- `advanceTime` guard clauses.
- `hasEventBefore`.
- `getNextEvent`.
- `getLogicalTime`.
- `isPaused`.
- `consumeDirty`.

A shared Haxe sequencer core is probably worthwhile, but it should come after Rack robustness work.

Good shared scope:

- time accumulation.
- pause/resume.
- reset hooks.
- event queue mechanics.
- dirty flag mechanics.
- finite positive delta guard.

Questionable shared scope:

- app state JSON schema.
- app output semantics.
- high-level musical interpretation.
- control UID policy before Layla/EDN metadata settles.

Possible Haxe shape:

```haxe
class SequencerCore {
    var currentTime:Float = 0;
    var paused:Bool = false;
    var dirty:Bool = true;
    var events:Array<Event> = [];

    public function advanceTime(delta:Float):Void {
        if (paused || !Math.isFinite(delta) || delta <= 0) return;
        currentTime += delta;
        advanceModel(delta);
    }

    function advanceModel(delta:Float):Void {}
}
```

The first migration should be one app with simple behavior. Do not migrate all apps until the first one proves that the abstraction improves clarity.

## OpenFL Cleanup

OpenFL duplication is real and is now being tackled after the Rack robustness work.

Shared pieces:

- `ComponentWorldBase` now handles coordinate mapping, component storage, mouse down/drag/up routing, `getView()`, and resize mapper rebuild for Gbloink, KDiagram, TileLand, Zewp, and TimeSlider.
- TimeSlider uses app-local `TimeSliderTrackComponent` instances for its four generated tracks, so track clicks now follow the same component UID plus `LocalPoint` contract as the other OpenFL apps.
- `OpenFLAppBase` now handles `ResponsivePanelHost`, timer setup, event draining, monitor instrument output, stage resize, mouse drag lifecycle, optional keyboard wiring, and frame callbacks.

TimeSlider still keeps its app-specific track-generation and redraw model. OpenFL and Rack input routing are no longer panel-wide: each track is an `IComponent`-style control, and the sequencer receives the track UID plus a point local to that track. The old `PLAY_AREA_UID` compatibility branch has been removed.

## Layout And UID Metadata

UID duplication exists in:

- Haxe views.
- Haxe sequencers.
- Rack parameter enums.
- Rack command dispatch.
- Rack widgets.
- generated composition.

Long-term, Layla plus EDN should generate or validate this metadata.

Near-term:

- centralize per-app maps.
- avoid changing IDs while doing robustness refactors.
- document transport IDs.
- document output IDs.

Later:

- generate UID constants for Haxe and C++ from the same metadata.
- reserve common UID ranges only if they make host integration simpler.

## What Should Stay App-Specific

Do not over-abstract:

- Gbloink ball simulation.
- TileLand trefoil grid/cursor behavior.
- KDiagram graph behavior.
- TimeSlider ramp behavior.
- Zewp agent behavior.
- Rack output topology.
- control snapshot contents.
- visual snapshot contents.
- app state schemas.
- manual app serializers.
- app-specific NanoVG drawing.
- Rack panel layout and HP choices.

These differences are the point of the framework. The framework should remove host and lifecycle boilerplate, not blur app identity.

## Guiding Principle

Consolidate host mechanics before app semantics.

The right abstractions are the ones that make adding a sixth app or a VST host boring: timing policy, persistence handoff, command queues, build rules, transport mapping, and generated metadata. The musical behavior, drawing personality, and state schemas should remain explicit until the framework has proved that a shared model actually fits them.
